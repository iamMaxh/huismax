# huismax: Architecture

How huismax.com is put together, where the boundaries are, and the rules that let several people or AI agents work on
it at the same time without breaking each other's work.

There are three companion documents:

| Document | Answers |
| --- | --- |
| **ARCHITECTURE.md** (this file) | How the system is layered, which way dependencies point, and the working rules |
| [PROJECT_MAP.md](PROJECT_MAP.md) | Where each file lives, which module it belongs to, and which files to touch for each feature |
| [DEPENDENCIES.md](DEPENDENCIES.md) | Packages, Cloudflare bindings, env vars and secrets, external services, and allowed internal imports |
| [CONTRACTS.md](CONTRACTS.md) | Every interface between modules: HTTP API, SSE, JSON islands, DOM hooks, storage keys, and external APIs |

The import rules in this document are enforced by `test/boundaries.test.ts`, which runs with `npm test`.

## 1. System at a glance

```
                      ┌──────────────────────── Cloudflare ────────────────────────┐
 browser ──HTTPS────▶ │ Worker "huismax" (src/index.tsx, Hono)                      │
   │                  │   ├─ server-rendered pages (hono/jsx, src/views)            │
   │                  │   ├─ /api/* JSON + SSE  (src/lib does the work)             │
   │                  │   ├─ ASSETS  public/ (client bundle, css, images)           │
   │                  │   ├─ D1  DB     CMS content, settings, messages, requests   │
   │                  │   ├─ KV  STATE  live/presence, Spotify tokens, rate limits  │
   │                  │   ├─ R2  MEDIA  photos, DJ covers                           │
   │                  │   └─ caches.default  edge cache for polled/external data    │
   │                  └──────────────┬─────────────────────────────────────────────┘
   │                                 │ fetch (server-side only, secrets stay here)
   │       ┌─────────────┬───────────┼──────────────┬───────────────┬──────────────────────┐
   │       ▼             ▼           ▼              ▼               ▼                      ▼
   │   Spotify API    LRCLIB     Resend (email)  Icecast radio  Monitoring API     Cloudflare Tunnel
   │                                             status-json    api.huismax.com    → bridge/ (Node, Max's server)
   │                                                                                 → OpenClaw (loopback)
   └──audio──▶ radio.huismax.com/live.mp3 (the browser streams it directly)
              download.huismax.com/latest.json (read by the worker for /muse)
```

**Runtime:** a single Cloudflare Worker (`wrangler.jsonc`, `main: src/index.tsx`). Nothing else is deployed from this
repository. `bridge/` runs separately on Max's own server. Branch previews get **no bindings and no secrets**
(`"previews": {}`), so every page has to render on its fallbacks.

**Build:** `scripts/build.mjs` (esbuild) bundles `client/main.ts` → `app-[hash].js`, `client/admin.ts` →
`admin-[hash].js`, and `client/styles/index.css` → `style-[hash].css` into `public/assets/`. It then writes the
hashed names to `src/generated/assets.ts`, which `src/views/layout.tsx` and `src/views/admin.tsx` read. Both outputs
are git-ignored and regenerated by `npm run build`, `dev`, `deploy` and `typecheck`.

## 2. Layers and dependency direction

Every file belongs to one layer. **A layer may only import from the layers below it.** Arrows point toward what is
imported.

```
 SERVER (Worker bundle)                                 CLIENT (browser bundles)

 L4  src/index.tsx            composition: routes,      C3  client/main.ts, client/admin.ts   composition
     │                        middleware, wiring            │
     ├──────────────┐                                       ▼
     ▼              ▼                                   C2  client/pages/*   client/admin/*   one module per page/area
 L3  src/views/*    (pure render: props in, JSX out)        │
     │                                                      ▼
     ▼  (types + listed pure constants only)            C1  client/lib/*     shared browser services (router, dom,
 L2  src/lib/*      domain services: env in, data out       │                chat, live, spotify, player…)
     │                                                      ▼
     ▼                                                  C0  type-only imports of server contract files
 L1  src/lib/env.ts, *-types.ts, cms.ts definitions,        (today: src/lib/homelab-types.ts)
     src/generated/assets.ts   contracts and config

 STANDALONE  bridge/*   (Node, imports only node:*)     scripts/*  (build tooling, not shipped)
```

Rules (enforced by `test/boundaries.test.ts`):

1. **`src/lib` never imports `src/views` or `src/index.tsx`.** Services don't know about pages.
2. **`src/views` import `src/lib` for types only**, plus a short allowlist of pure constants (`STATUS_PRESETS`,
   `MAX_NAME`, `MAX_REQUEST`, `RANGES`). Views never fetch, read KV or D1, or call a service. Everything they show
   comes in through props.
3. **`client/*` never imports `src/*` at runtime.** It may use `import type` from the server contract files listed in
   the test (today only `src/lib/homelab-types.ts`). Anything else crosses the wire as JSON (see CONTRACTS.md).
4. **`client/lib` never imports `client/pages` or `client/admin`.** Shared code doesn't know its callers.
5. **The public bundle (`client/main.ts`, `client/pages`, `client/lib`) doesn't import `client/admin`.** There is one
   exception, `client/pages/homelab.ts` → `client/admin/h.ts` (a tiny DOM helper), which is allowlisted until
   Phase 2 moves `h.ts` to `client/lib`.
6. **`bridge/` imports only `node:*` built-ins.** It's deployed by hand onto another machine.
7. **`scripts/` is build tooling only.** Nothing in `src/` or `client/` imports it.

Why it matters for parallel work: when dependencies only point downward, a change to a page (L3/C2) can never break a
service (L2) or another page. Only changes to L1/L2/C1 can spread, and those are the files marked 🔴/🟠 in
PROJECT_MAP.md.

## 3. Modules (feature boundaries)

The site is split into **feature modules**. A module owns a vertical slice: its service code in `src/lib`, its view,
its client page and its CSS. Each module is listed in full in PROJECT_MAP.md.

| Module | What it is | Public surface (contract) |
| --- | --- | --- |
| `platform` | Worker entry, middleware, layout, router, design tokens, build, test | Page shell, `PageInit`, `Scope`, the `data-page` key, CSS tokens |
| `cms` | Collections, settings, migrations, public content reads | `COLLECTIONS`, `Settings`, `content.*` readers, D1 schema |
| `admin` | /admin UI and all `/api/admin/*` + admin-only writes | Admin HTTP API, `admin-initial` island |
| `live` | Live status, radio (Icecast), presence | `/api/live-status`, `/api/dj-status`, `/api/presence`, `live-initial` |
| `spotify` | Now playing, recent, lyrics, OAuth link | `/api/spotify/*` |
| `dj` | /dj page, sessions (mixes), song requests | `/api/dj/requests`, `mix-data` island |
| `gallery` | /photographer, /hiking, photo uploads, /media | `/media/:key`, `photo-data` island, R2 prefixes |
| `pages-static` | /, /vibe-coder, /music, /now, /404 | `project-data` island |
| `reply` | /reply contact form, messages, email | `/api/reply`, messages table |
| `chat` | Live chat panel, worker proxy, bridge | `/api/chat` SSE, bridge `POST /chat` |
| `homelab` | /homelab dashboard and its Monitoring API client | `/api/homelab*`, `homelab-types.ts`, MONITORING_API.md |
| `muse` | /muse tutorial page and installer release lookup | `museRelease()`, `latest.json` |

**A module may use another module only through its public surface:** an exported function of a `src/lib` file, an
HTTP endpoint, or a JSON island. It may never reach into another module's KV keys, D1 tables, DOM nodes or CSS
classes. Concretely:

- KV keys and D1 tables have a single owning module (CONTRACTS.md §9). Only the owner reads or writes them directly.
  Everyone else calls the owner's function (`getLiveStatus`, `content.items`, …).
- CSS: `client/styles/pages/<page>.css` styles that page only, using the page's own class prefix (CONTRACTS.md §7:
  `.hl-` homelab, `.mu-` muse, `.console-`/`.mix-` dj, …). Shared look goes in `tokens.css`/`components.css` (🔴 platform).
- Client: a page module only touches nodes inside the `main` it was given, and registers every listener, timer and
  loop on the `Scope` it was given.

## 4. Request lifecycle

**Page request** (`GET /dj`):

1. Middleware: a `www.` host is sent with a 301 to the apex. A trailing slash is sent with a 301 to the path without it.
2. Route → `page(c, key, title, body)` in `src/index.tsx`:
   - loads `getLiveStatus` and `content.site` in parallel;
   - a page hidden in `/admin` (`settings.pages[key] === false`) returns 404 to visitors (admins still see it);
   - the route's own data comes from `src/lib/content.ts` readers, which **never throw** and fall back to defaults.
3. The view (`src/views/pages/*.tsx`) renders inside `Layout`, which adds the head, nav, audio bar, chat shell and the
   `site-nav` + `live-initial` JSON islands. `<body>` and `<main>` carry `data-page="<key>"`.
4. In the browser, `client/main.ts` runs `mount(main)`, which calls `pages[main.dataset.page](main, scope, navigate)`.
5. Navigation: `client/lib/router.ts` intercepts same-origin links, fetches the next page (`X-Router: 1`), swaps only
   `<main>`, calls `scope.dispose()` on the old page, then `mount()` on the new one. The header, audio bar and chat
   survive. On any failure it falls back to a full page load.

**API request** (`GET /api/spotify/now`): route → `edgeData` (edge cache by path, TTL chosen per answer) → lib
service → `fresh()` JSON with `Cache-Control: no-store` for the browser. Errors are always JSON `{ error }` under
`/api/*` (CONTRACTS.md §1).

**Admin write** (`PATCH /api/admin/c/dj/:id`): `guardDb` = `isAdmin` (cookie `hm_admin` or `Bearer ADMIN_TOKEN`) +
`sameOrigin` + D1 bound + `ensureDb` → `cms.update` (validates against `COLLECTIONS.dj.fields`) → JSON item.

**Chat** (`POST /api/chat`): `sameOrigin` → `src/lib/chat.ts` validates and adds a hashed visitor id → the bridge
through the Tunnel (`Bearer CHAT_BRIDGE_SECRET`) → OpenClaw. The SSE events are relayed unchanged, and bridge error
text never reaches the browser.

## 5. Data and state

| Store | Binding | Holds | Owner rules |
| --- | --- | --- | --- |
| D1 | `DB` | CMS collections, settings, messages, DJ requests | Schema only through new numbered `migrations/NNNN_*.sql`, **additive only**. Applied by the worker itself (`src/lib/db.ts → ensureDb`), and also compatible with `wrangler d1 migrations apply`. |
| KV | `STATE` | live override, presence, Spotify tokens, rate-limit counters, admin login fails, legacy `mixes` | Each key prefix has one owner (CONTRACTS.md §9). Writes are rare: no per-request writes on public reads. |
| R2 | `MEDIA` | photo originals + thumbs, DJ covers | Keys only via `media.putImage`, served only via `/media/:key` after `validKey` + a publish check. |
| Edge cache | `caches.default` | Spotify now/recent/lyrics, radio status, homelab data, Muse release | Synthetic keys (CONTRACTS.md §9). Cache only "good" answers. Setup and error states are not kept. |
| Static | `ASSETS` | `public/` | Hashed `/assets/*` are immutable (`public/_headers`). |

Every binding is **optional** in `Env`. Code checks for it and degrades: no D1 → defaults and fallback identities; no
KV → no live override or presence; no R2 → no photos. That is what keeps previews and local dev working.

## 6. Security model

- **Secrets stay server-side.** The browser never receives `ADMIN_TOKEN`, `SPOTIFY_CLIENT_SECRET`, `RESEND_API_KEY`,
  `CHAT_BRIDGE_SECRET`, `MONITORING_API_TOKEN`, Spotify tokens, or private settings (`replyTo`, `replyFrom`;
  `PRIVATE_SETTINGS` in `cms.ts`). The `site-nav` island carries only menu labels and hrefs.
- **Admin auth:** cookie `hm_admin` = HMAC(ADMIN_TOKEN). It is `httpOnly`, `SameSite=Lax` and lasts 30 days. Scripts
  use `Authorization: Bearer <ADMIN_TOKEN>`. Every state-changing route also checks `sameOrigin()`. Login allows 5
  failures per IP per 5 min (KV).
- **Public writes** (`/api/reply`, `/api/dj/requests`, `/api/chat`) need `sameOrigin`, a honeypot (`website` field),
  per-IP-bucket limits (hashed, KV) and global hourly caps. Chat limits live in the bridge.
- **Outbound URLs** are allowlisted where they come from data (`muse-release.ts` ALLOWED, `chat.ts` `bridgeUrl` =
  https only, CMS `url` fields = http(s) only, homelab services = https only).
- **SQL:** table and column names only ever come from `COLLECTIONS` definitions. Values are always bound.
- **Infrastructure** (DNS, Tunnel, Access, firewall, the Monitoring API host, the Finance API) is **out of scope for
  this repository**. No task here changes it.

## 7. Rules for parallel / multi-AI development

These rules are what keeps the parts from breaking each other. Every agent working in this repository follows them.

### 7.1 Scope a task to one module

- Each task names its **module** (§3) and stays inside that module's files (PROJECT_MAP.md).
- Files are tagged 🟢 module-owned, 🟠 shared contract, or 🔴 platform core.
  - 🟢 Change freely within the task.
  - 🟠 Additive changes only (new optional fields, new endpoints, new exports). Update CONTRACTS.md in the same PR.
  - 🔴 Only when the task is explicitly about it, or with an additive, minimal edit that the PR description calls out
    (e.g. registering a new page in `client/main.ts`, `layout.tsx` `PageKey`, `site.ts` `PATHS`).
- Two tasks running at once must not both change the same 🔴 file. If they would, do them one after the other.

### 7.2 Contracts change by addition

- **Never** rename or remove a field, endpoint, island id, `data-*` hook, KV key, table, column or CSS token that
  something else reads. Add the new one, move readers over, and remove the old one only in a later, dedicated cleanup
  task.
- New response fields are optional for readers. Readers ignore fields they don't know.
- Breaking shape changes to a cached answer bump a version in the cache key (see `LYRICS_VERSION`).
- D1: a new numbered migration, additive only (`CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN` with a
  default, guarded `UPDATE`s). Never edit an applied migration.

### 7.3 Adding things: the recipes

- **New page `/foo`:**
  1. Add `src/views/pages/foo.tsx` (🟢).
  2. Add the route in `src/index.tsx` with `page(c, 'foo', …)` (🔴, additive).
  3. Add `'foo'` to `PageKey` in `layout.tsx` (🔴, additive).
  4. Optional: `client/pages/foo.ts` exporting `initFoo: PageInit`, registered in `client/main.ts` (🔴, additive).
  5. Add `client/styles/pages/foo.css` and its `@import` in `index.css` (🔴, additive).
  6. If it should appear in the menu or palette, update `site.ts` (🔴). If it should be hideable, update
     `PAGE_KEYS`/`HIDEABLE` (🔴).
- **New public API:** a service function in `src/lib/foo.ts` (env in, never throws for reads) + a route + a CONTRACTS.md
  row + a test in `test/foo.test.ts`.
- **New CMS collection:** a migration + an entry in `COLLECTIONS` + mirrored types in `client/admin/api.ts`. The admin
  UI builds its forms from `defs`, so most of the work is the definition.
- **New secret or var:** add it to `Env` (`env.ts`), `.dev.vars.example` (placeholder only) and DEPENDENCIES.md, and
  add a "missing" behaviour. Never put a real value in the repository.

### 7.4 Done means

- `npm run typecheck` passes (server + client + the build).
- `npm test` passes (including `boundaries.test.ts`). Run the relevant subset with `npm test -- <name>`.
- CONTRACTS.md / PROJECT_MAP.md / DEPENDENCIES.md are updated if the change touches what they describe.
- No secrets, no production URLs in preview-only code, and no behaviour change outside the task's module.

## 8. Known debt and refactor phases

The site works. The aim of these phases is to make it safer to change, with **no behaviour change in any phase**.
Each phase is its own PR and can be done by one agent at a time.

| Phase | Change | Why |
| --- | --- | --- |
| **0** (this PR) | ARCHITECTURE / PROJECT_MAP / DEPENDENCIES / CONTRACTS + `test/boundaries.test.ts` | Write down the boundaries and guard the ones that already hold |
| **1** | Split `src/index.tsx` (all routes, ~730 lines) into `src/routes/<module>.tsx`, each exporting a Hono sub-app. Move the shared helpers (`page`, `guard`, `guardDb`, `body`, `str`, `fresh`, `edgeData`) into `src/http.tsx`. `index.tsx` keeps only middleware, mounting and the fallbacks. | Today every feature edits the same file, which is the #1 merge-conflict hotspot |
| **2** | Add a `src/contracts/` folder of type-only files for every JSON shape the browser reads (live, presence, spotify, lyrics, homelab, admin). `client/admin/api.ts` re-exports from it instead of copying by hand. Move `client/admin/h.ts` → `client/lib/h.ts`. Tighten the boundary test to "client may `import type` only from `src/contracts`". | Removes type drift between server and client (`client/admin/api.ts` is a manual copy today) |
| **3** | Contract tests per endpoint (status + shape against the `src/contracts` types). Add a CI workflow running `typecheck` + `test` on every PR. | Lets reviewers trust a green PR from any agent |
| **4** | Per-module ownership files (CODEOWNERS-style), if more than one human starts reviewing | Optional |

Other known debt (no phase yet):

- The `homelab` "four metrics side by side" test depends on the clock and is occasionally flaky.
- `SITE_FEATURES.md` is a reference for the assistant (OpenClaw), not for developers. Keep it in sync when public
  behaviour changes.
